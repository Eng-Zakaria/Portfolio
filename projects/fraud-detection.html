The Problem

Fraud has to be caught while a payment is still being authorised; a nightly batch job flags it too late. This personal project builds the pieces a streaming fraud system needs (an event stream, per-transaction scoring, alerts, a dashboard and a retraining schedule) and runs them on synthetic transactions from a Python generator with a 2% fraud rate. It is a learning build, not a production system.

Architecture

 TransactionStreamSimulator (synthetic)     Airflow DAG (every 6 h)
            |                                   generate -> clean -> load -> train -> evaluate
            v                                                       |          |
 Kafka topic "transactions" (key: transaction_id)               MLflow    Postgres model_metrics
            |
            v
 Kafka consumer ----+----> FraudDetector (scikit-learn) <---- FastAPI /predict
                      |      score + risk tier
                      v
 Kafka topic "fraud_alerts"  (no consumer yet)

 MonitoringSystem polls Postgres every 5 min ---> Slack / email / webhook
 Plotly/Dash dashboard re-queries Postgres every 30 s
 Redis: daily prediction / alert counters

Implementation

  • Kafka Streaming: A producer writes synthetic transactions to a transactions topic keyed by transaction ID (acks='all', 3 retries); a consumer group scores each message and commits offsets after every poll
  • Feature Engineering: Temporal, amount, per-user history, location-distance, device-reuse and merchant features, all standard-scaled. At scoring time the history is rebuilt from the request itself, so per-user features carry little signal yet
  • Model Serving: The same scikit-learn detector sits behind the Kafka consumer and a FastAPI service (/predict, /predict/batch, /health). Redis holds daily prediction and alert counters, not features
  • Monitoring: A Plotly/Dash dashboard shows transaction volume, fraud trends, merchant risk, hourly patterns, recent alerts and model metrics, refreshing every 30 seconds from Postgres
  • Alerting: Slack, email and webhook handlers fire on aggregate rules checked every 5 minutes: a 3x hour-over-hour fraud-rate spike, fraud rate above 10%, AUC-ROC falling 10% or below 0.7, and health and data-quality checks. Per-transaction alerts go to a fraud_alerts Kafka topic that nothing consumes yet
  • Model Monitoring: Performance-degradation alerts on stored AUC-ROC; there is no feature-distribution drift check. Retraining runs on a 6-hour Airflow schedule, not on an alert trigger
  • Docker: Docker Compose runs the infrastructure (Postgres, Redis, Kafka, Zookeeper, Airflow, MLflow); the Python services are started by hand

ML Models

  • Random Forest: Baseline model for transaction classification
  • Gradient Boosting: Improved accuracy through ensemble boosting
  • Logistic Regression: Interpretable model for explainability requirements

Training compares all three on validation AUC-ROC, optionally grid-searches the winner, and logs runs to MLflow. No trained models or metric reports are saved in the repository, and the synthetic data contains a label-derived fraud_score column that leaks into the features, so any score from this pipeline would be inflated until that is removed.

Outcome

The project covers the full shape of a streaming fraud system: ingestion, scoring, alerting, a dashboard and scheduled retraining. Scoring latency and model accuracy have not been measured, so no performance numbers are claimed.

A close read of the code found bugs to fix before any benchmark: feature leakage from the synthetic data, an alerting import error, a risk-tier ordering bug, and a model path mismatch between training and the API. The write-up covers each one and the plan to measure latency and add real drift checks.
