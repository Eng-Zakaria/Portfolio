What v1 Is (and Is Not)

Built in v1: the scraper framework, one HTML source (SparkFun), one API source (Mouser), local bronze landing, the schema-drift quality gate, the cdp CLI and an Airflow DAG that ties the pieces together. Roadmap, not delivered: the Glue/Spark transform job, the Redshift warehouse schema and the analytics API are tracked in docs/roadmap.md — nothing downstream of bronze is claimed as working today.

The Problem

Electronics component data lives behind HTML that no one owns. Scraper code written against a specific layout works until the site redesigns, and when it breaks it breaks quietly — selectors return null, the pipeline still runs green, and a warehouse full of empty prices looks exactly like a healthy one until someone orders from it. The second problem is legal rather than technical: some of the most useful component suppliers forbid scraping in their terms of service, and the framework has to stay usable by people who do not want to remember which command loads a fixture or which cron entry exists.

Approach & Implementation

  • Config-Driven Sources: each source is a YAML file under configs/sources/ describing selectors, pagination and field mapping — a site redesign becomes a config edit, not a code change.
  • v1 Sources: SparkFun (HTML), Texas Instruments (HTML), and Mouser Electronics via its free public API — chosen deliberately as a ToS-compliant channel instead of scraping a site that would rather you use its API.
  • Schema-Drift Gate: if a selector that used to return data suddenly returns nulls across a large share of records, the run fails loudly instead of silently loading empty fields.
  • Layered Flow: web sources and APIs → scraper or API client → bronze landing zone (JSONL locally, an S3 prefix in prod, where only ingestion/landing.py changes) → transform (clean, dedupe, type) → silver/gold dimensional warehouse → analytics layer (API + dashboard).
  • Orchestration: an Airflow DAG runs the chain with a data-quality gate sitting between ingestion and transform, so nothing downstream sees drifted data.
  • cdp CLI: doctor, sources list/info (live robots.txt check plus a pre-run checklist), run (single source or all), check, status (reads a run log of record counts, pass/fail and timestamps), schedule (prints or installs a cron line) and test. The cron line is convenience only — Airflow is the real orchestrator, owning retries, alerting and per-task observability.
  • Offline Tests: tests run against saved HTML fixtures, so CI needs no network and cannot be broken by a source outage.
  • Compliance Built In: robots.txt checks, polite per-source rate limiting from config, and docs/sources_evaluated.md recording why a deferred source was deferred — for example, LCSC disallows scraping in its ToS.

Challenges & Solutions

Challenge: HTML Layouts Change and Break Pipelines Silently

A class rename or markup restructure makes selectors return null, and a naive scraper treats that as "no data today" instead of a failure.

Solution: Config-Driven Selectors + a Gate That Fails the Run

Selectors live in config so a redesign is a one-file change, and a selector that starts returning nulls across a large share of records aborts the run loudly rather than loading empty fields.

Challenge: Pointing a Scraper at a Site That Forbids It

Scraping a supplier whose terms of service prohibit it is a legal and reputational problem, not just an engineering one.

Solution: Prefer the API, Respect robots.txt, Document Decisions

Where a free public API exists it is used instead — Mouser replaces a would-be scrape — alongside robots.txt checks, polite per-source rate limits, and a written record in docs/sources_evaluated.md of why each deferred source was deferred.

Challenge: Developers Needing to Run Scrapers Ad Hoc

Without a single entry point, ad-hoc runs mean reading source code to work out the right invocation and options.

Solution: One CLI From Health Checks to Scheduling

The cdp command covers the whole lifecycle: doctor, sources info with a live robots.txt check, run, check, status from the run log, schedule and test.

Challenge: Network-Dependent Tests

Tests that hit live sites are slow, flaky and unfair to rate limits — and they fail for reasons unrelated to the code.

Solution: Fixture-Based Tests That Run Offline

Saved HTML fixtures make the test suite deterministic and network-free, so CI validates parsing logic rather than a website's uptime.

Outcome

A reusable ingestion framework where adding a source is one YAML file, with correctness enforced by a quality gate rather than by inspection — a drifting schema stops the run instead of quietly loading empty fields into a warehouse. The honest boundary of v1: ingestion, landing and the gate are built and tested offline; the transform job, warehouse schema and analytics API are roadmap items in docs/roadmap.md.
