Scope & open items

Built in v1: the config-driven scraper framework, two HTML source configs (SparkFun, Texas Instruments), one API client (Mouser), local bronze landing, the schema-drift quality gate, the seven-command cdp CLI and three offline fixture tests, all passing. Skeleton: an Airflow DAG lays out the intended task structure. Next: rendered (JavaScript) scraping, the Glue/Spark transform job, the Redshift warehouse schema and the analytics API, tracked in docs/roadmap.md.

Live run: on 2026-08-07 the gate stopped a SparkFun run because product_name was null in 64% of 791 records, over the 50% threshold. That is the gate doing its job; updating the SparkFun selectors for a passing live run is the next step.

The Problem

Electronics component data lives behind HTML that no one owns. Scraper code written against a specific layout works until the site redesigns, and when it breaks it breaks quietly — selectors return null, the pipeline still runs green, and a warehouse full of empty prices looks exactly like a healthy one until someone orders from it. The second problem is legal rather than technical: some of the most useful component suppliers forbid scraping in their terms of service, and the framework has to stay usable by people who do not want to remember which command loads a fixture or which cron entry exists.

Architecture

Approach & Implementation

  • Config-Driven Sources: each source is a YAML file under configs/sources/ describing selectors, pagination and field mapping. For static HTML, a site redesign becomes a config edit, and a new source can be added with one YAML file through the CLI. JavaScript-rendered pages are on the roadmap.
  • v1 Sources: SparkFun (HTML), Texas Instruments (HTML), and Mouser Electronics via its free public API — chosen deliberately as a ToS-compliant channel instead of scraping a site that would rather you use its API.
  • Schema-Drift Gate: the scraper checks null rates on required fields (50% threshold) and the landing validator checks them again (30% threshold). Either check raises before records land, so the run fails loudly instead of silently loading empty fields.
  • Layered Flow (built): web sources and APIs → scraper or API client → gate → bronze landing zone (JSONL locally; moving to an S3 prefix would only change ingestion/landing.py). Planned: transform (clean, dedupe, type) → silver/gold dimensional warehouse → analytics layer.
  • Orchestration: cdp schedule prints or installs a cron line for the CLI today. An Airflow DAG skeleton lays out the intended scrape → validate tasks; switching it to call cdp with sources read from config is next.
  • cdp CLI (seven commands): doctor, sources list/info (live robots.txt check plus a pre-run checklist), run (single source or all), check, status (reads a run log of record counts, pass/fail and timestamps), schedule and test.
  • Offline Tests: three tests run against a saved HTML fixture, so they need no network and cannot be broken by a source outage. All three pass.
  • Compliance Built In: robots.txt checks, polite per-source rate limiting from config, and docs/sources_evaluated.md recording why a deferred source was deferred — for example, LCSC disallows scraping in its ToS.

Challenges & Solutions

Challenge: HTML Layouts Change and Break Pipelines Silently

A class rename or markup restructure makes selectors return null, and a naive scraper treats that as "no data today" instead of a failure.

Solution: Config-Driven Selectors + a Gate That Fails the Run

Selectors live in config, so a redesign of a static page is a one-file change. A selector that starts returning nulls across a large share of records aborts the run loudly rather than loading empty fields. The last live SparkFun run was stopped exactly this way.

Challenge: Pointing a Scraper at a Site That Forbids It

Scraping a supplier whose terms of service prohibit it is a legal and reputational problem, not just an engineering one.

Solution: Prefer the API, Respect robots.txt, Document Decisions

Where a free public API exists it is used instead — Mouser replaces a would-be scrape — alongside robots.txt checks, polite per-source rate limits, and a written record in docs/sources_evaluated.md of why each deferred source was deferred.

Challenge: Developers Needing to Run Scrapers Ad Hoc

Without a single entry point, ad-hoc runs mean reading source code to work out the right invocation and options.

Solution: One CLI From Health Checks to Scheduling

The cdp command covers the whole lifecycle: doctor, sources info with a live robots.txt check, run, check, status from the run log, schedule and test.

Challenge: Network-Dependent Tests

Tests that hit live sites are slow, flaky and unfair to rate limits — and they fail for reasons unrelated to the code.

Solution: Fixture-Based Tests That Run Offline

Saved HTML fixtures make the test suite deterministic and network-free, so CI validates parsing logic rather than a website's uptime.

Outcome

A reusable ingestion framework where a static HTML source is one YAML file, with correctness enforced by a quality gate rather than by inspection. A drifting schema stops the run before anything lands. The gate has already proven itself live: it blocked a SparkFun run with 64% null product names.
