The Problem

Blockchain forensic analysis requires processing large volumes of Ethereum transaction data to identify suspicious patterns like chain hopping, smurfing, and peel chains. The question I wanted to test was whether a graph database (Neo4j) or a batch engine (PySpark) is the better fit for multi-hop tracing and pattern detection.

Traditional batch processing struggles with relationship-heavy queries that require traversing multiple transaction hops, while graph databases excel at these operations but may not scale as efficiently for simple aggregations.

Architecture

 Sources     synthetic generator (1,000 txs) | Infura JSON-RPC (last 3 blocks)
      |
 ETL         Bronze -> Silver -> Gold   (pandas-backed Spark-like API)
      |
      +--> Graph      (:Wallet)-[:SENT]->(:Transaction)-[:RECEIVED]->(:Wallet)
      +--> Benchmark  wallet degree | multi-hop | high-frequency wallets
      +--> Search     Elasticsearch mappings + Kibana dashboard config
 Detectors   chain hopping | smurfing | peel chains | wallet scoring

Benchmarking Results

The benchmarking module times the same three operations on both sides and reports the ratio and a winner per operation:

  • Multi-hop Traversal: a Cypher [:SENT*1..3] path query against a hop-by-hop DataFrame lookup
  • High-frequency Wallets: wallets with more than 100 transactions, as a Cypher count against a group-by
  • Wallet Degree: transactions touching one wallet, as a relationship count against a filter

Current status: the harness runs end to end, but the default run uses a mock Neo4j client and a pandas stand-in for Spark on synthetic data, so its sub-millisecond ratios do not compare the two engines. A fair result needs a live Neo4j and SparkSession, the same mainnet snapshot in both, and repeated warm runs.

Implementation

  • Data Ingestion: Infura JSON-RPC client for recent mainnet blocks, a Web3.py bulk fetcher script, and a synthetic generator for offline runs
  • Medallion Architecture: Bronze (validation, address normalization), Silver (dedupe, wei-to-ETH, gas cost, tx type) and Gold (per-wallet stats, risk tier) layers
  • Threat Detection: Unit-tested detectors for fan-out (chain hopping), smurfing and 2–3 hop peel chains, plus additive wallet risk scoring; not yet called from the main run
  • Graph Modeling: Neo4j schema with wallets and transactions as nodes, linked by SENT and RECEIVED, with uniqueness constraints and batched UNWIND/MERGE ingest
  • Visualization: Generated Elasticsearch mappings and a Kibana dashboard config; indexing currently goes to an in-memory stand-in
  • Docker Deployment: docker-compose for Elasticsearch, Kibana and Neo4j 5.15

Intended Use Cases

  • AML/CFT compliance monitoring for financial institutions
  • Forensic transaction tracing for law enforcement
  • DeFi protocol analysis and risk assessment
  • Wallet behavior profiling and anomaly detection

Outcome

A working prototype: the pipeline, detectors, graph schema and benchmark harness run locally without infrastructure. The next step is running the harness against live Neo4j and Spark on a fixed mainnet block range, aligning the multi-hop query with the Wallet→Transaction→Wallet schema, and wiring the detectors into the main run.
