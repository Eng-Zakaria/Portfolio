The Problem

Blockchain and market data arrive from many endpoints — Ethereum nodes, Bitcoin RPC, and exchange APIs. Wallet addresses are stable identifiers, and PII can hide in memos, labels, and metadata. Pseudonymised data is still personal data under GDPR, so serving it without masking, retention, and erasure controls creates risk.

The aggregator puts a privacy layer in front of analytics: mask identifiers and free-text PII, record processing steps with timing in an audit table, and schedule deletion. Export and erasure exist only as logging helpers so far, and the Fernet encryption methods are defined but not called.

Architecture

Approach & Implementation

  • Sources: Ethereum via web3.py HTTP provider, Bitcoin via raw JSON-RPC over requests, and market APIs — Binance via ccxt, CoinGecko, and Alpha Vantage.
  • Masking layer: 8 regex PII patterns (email, phone, SSN, card, IBAN, street address, IPv4, wallet) with partial, full, hash (unsalted SHA-256), and tokenize (unsalted MD5) modes; sender and recipient addresses truncated to prefix and suffix. Plain strings inside lists (Bitcoin output addresses, Ethereum log topics) are not yet masked.
  • Audit log: audit_logs table written from flow-analysis and market processing with record counts and processing_time_ms; API reads are not yet logged, and the export and erasure helpers have no callers.
  • Retention: DataRetention ledger (365-day default) and cleanup jobs for data and audit logs, implemented but not wired into ingestion or scheduled.
  • Analytics: networkx, pandas, and numpy flow analysis: z-score amount and frequency anomalies plus circular-flow detection.
  • Storage: SQLAlchemy models for PostgreSQL. A Docker Compose file also lists Elasticsearch 8.11, MongoDB 7, and Redis 7, but the app code does not use them yet.
  • Scheduling & serving: FastAPI on :8000 with no authentication yet. Compose defines Celery worker/beat and Nginx, but the Celery app module and Nginx config are not in the repo; rate limits are documented, not implemented.
  • Observability: prometheus-client metrics in the app; Prometheus and Grafana containers in Compose without their config files; Sentry DSN setting present but not initialised.

Challenges & Solutions

Challenge: PII in chain and market payloads

Emails, phones, card numbers, IBANs, and wallet-linked labels can appear anywhere in free-text fields across chains and APIs.

Solution: Masking gate with modes

One pipeline every ingestor calls: regex masking across 8 PII patterns with partial, full, hash, and tokenize modes, plus shape-preserving truncation of addresses. Truncation and unsalted hashes can be matched back against the public ledger, so a keyed HMAC is the planned next step.

Challenge: Provable retention and erasure

Compliance needs proof of what ran, how long it took, and what was exported or erased.

Solution: Audit table plus retention ledger

Processing steps are written to an audit-log table with processing_time_ms, and a DataRetention ledger records scheduled and completed deletions (365-day data and 2555-day audit defaults). Export and erasure flows, and a scheduler for cleanup, are still to be built.

Outcome

The codebase routes Ethereum, Bitcoin, and market records through one masking pipeline before they reach the API and flow analysis, with an audit table and retention ledger alongside. It has not been run end to end: a pydantic v2 import error and an encryption-key mismatch (a 32-character validator vs. Fernet's 44-character key) stop it at startup, so there are no runtime numbers.

Next steps are keyed pseudonyms, wiring storage and scheduled cleanup, an erasure endpoint with a suppression list, and authenticated, audited reads. Local project — no public GitHub link.
