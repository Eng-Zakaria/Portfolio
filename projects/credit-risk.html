Credit Risk — Score-and-Decide

Credit risk analysis: a scoring pipeline with synthetic data, gradient-boosted PD models behind a validation gate, and a FastAPI approve/review/decline endpoint.

Validation Gate

The code defines the gate a model must pass before the training DAG deploys it, measured on a held-out 20% test split:

Check Threshold Effect
Test AUC-ROC ≥ 0.70 Blocks deploy
Gini (2·AUC − 1) ≥ 0.40 Blocks deploy
KS statistic ≥ 0.30 Blocks deploy
Train − test AUC gap ≤ 0.05 Warning
PSI, train vs test scores ≤ 0.20 Warning

The Problem

The goal was to build the machinery around a credit model, not just the model: a repeatable feature pipeline, a training run with a validation gate, a scoring API that returns a decision, and scheduled jobs for retraining and drift monitoring, all on synthetic data.

A model is only useful once it is trained, validated, deployed and monitored the same way every time; that lifecycle is what keeps drift and reproducibility problems in check.

Architecture

FastAPI /predict         PD -> risk band -> APPROVE / REVIEW / DECLINE

Implementation

  • Synthetic Data: Generator for 100,000 correlated applications (demographics, credit history, loan terms, utilization) with a logistic default formula adjusted to a 15% default rate
  • Feature Pipeline: scikit-learn ColumnTransformer with median fill, 1–99% winsorizing, standard scaling and target encoding, fitted on the training split only
  • Models: XGBoost, LightGBM and CatBoost wrappers with early stopping; a weighted-average ensemble, a stacking ensemble with a logistic meta-learner, and PyTorch MLP and TabTransformer classes (the default run trains the three boosters)
  • Orchestration: Airflow training DAG (weekly: load, features, three parallel trainers, evaluate, validate, deploy) and monitoring DAG (daily drift check and report)
  • Experiment Tracking: MLflow logs parameters and metrics per run; models are saved with joblib
  • Scoring API: FastAPI with Pydantic input validation, mapping probability of default to five risk bands and APPROVE / REVIEW / DECLINE
  • Risk Metrics: AUC, Gini, KS, Brier score, lift, PSI and expected loss (PD × LGD × EAD); DuckDB data mart with SQL written to be BigQuery-compatible

Key Design Decisions

  • Generated the data with a known default formula, so the true signal is known and every run is reproducible from a seed; the trade-off is that scores say nothing about real borrowers
  • Made AUC, Gini and KS minimums blocking and kept overfit gap, PSI and decile ordering as warnings, so the gate does not trip on noise
  • Returned a decision rather than a raw probability, with a wide REVIEW band (PD 0.20–0.50) that sends borderline applicants to a person
  • Kept models behind one fit / predict_proba / save interface so new model types plug into the same training and validation steps

Outcome

The repository contains each stage of a score-and-decide loop: data generation, feature pipeline, training with a validation gate, a deploy step, a scoring API and drift monitoring, with tests for the models, metrics and data generator.

Next steps:

  • Align the deploy and API model paths so the API serves what the gate approved.
  • Run the drift check on fresh scoring data and wire the retraining trigger.
  • Record a full training run and publish its gate results.
