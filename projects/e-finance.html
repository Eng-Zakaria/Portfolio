Portfolio scaffold for a digital bank: six services, a Postgres schema and three Airflow DAGs in one Docker Compose file. The core-banking API holds most of the real logic; several services still run on in-memory or sample data.

The Problem

A bank has to move money correctly on the request path — a transfer debits one account and credits another, or neither happens — while batch work (interest accrual, daily summaries, fraud review) runs off that path.

This project is one repository that shows both sides: a service split, a schema that stores money as integer minor units, and Airflow DAGs that run batch jobs against the same Postgres data.

Approach & Implementation

  • Core banking API (FastAPI): 44 routes for auth, users, accounts, cards and transactions. Internal transfers write a debit and a credit row and update both balances in one database commit; amounts are BIGINT minor units.
  • Transaction service (Spring Boot): 10 routes; saves transaction records to its own database and publishes them to the Kafka topic transactions, keyed by reference number. No consumer exists in the repo yet, and its fraud call is stubbed out.
  • Storage: PostgreSQL is the system of record (320-line schema, 10 tables). MongoDB and Redis are in Compose and connected at API startup but not used by any code path yet; Elasticsearch appears only as config.
  • Risk & credit scoring: fraud-detection blends 8 hand-written rules with a random forest and isolation forest that are fitted on placeholder data until real models are saved. BNPL computes a 300–850 score from four weighted factors over in-memory orders.
  • Batch & monitoring: 3 Airflow DAGs — daily transaction ETL with idempotent upserts, daily interest accrual with a monthly credit, and a 15-minute fraud-alert sweep. Prometheus scrape config covers all six services.

Challenges & Solutions

Challenge: Keeping a transfer consistent

A transfer must never debit one account without crediting the other, and money must not pick up floating-point rounding.

Solution: Two legs, one commit, integer cents

Both transaction rows and both balance updates go in a single SQLAlchemy commit, with ownership, status and limit checks first. Still missing: row locking for concurrent transfers and an idempotency key for client retries.

Challenge: Batch work off the request path

Interest accrual, daily summaries and fraud review should not run inside the API process.

Solution: Airflow DAGs on PostgresHook

Scheduled DAGs write to the same Postgres with ON CONFLICT upserts so ETL re-runs overwrite rather than duplicate. Known gaps: the ETL transform step still returns fixed values, and interest accrual is not atomic or guarded against re-runs.

Outcome

The repository has six services, a Postgres schema, three DAGs and monitoring config in one Compose file, with the core-banking money paths implemented and ownership-checked behind JWT auth (bcrypt, lockout, TOTP 2FA).

It does not boot end to end as committed: three services have no Dockerfile, the core API imports two missing modules, and there are no automated tests. Next steps are making it boot, locking balances during transfers, adding idempotency keys, and wiring a real Kafka consumer.
