Hadith QA — Arabic Q&A Web App

Django web app for asking questions about hadith, backed by a question-answering model the team hosted on Hugging Face.

The Problem

Searching hadith collections usually means knowing which book to open and which words to try. The project, Estidlal, aimed to let students and researchers search religious sources with a question, phrase, or word instead.

This was a Helwan University graduation project built by a six-person team. The question-answering model ran in a Hugging Face Space on a teammate's account (Mohamed-Maher/Hadith-QA-System); its data, retrieval and model code are not in this repository. This repository is the Django web app: sign-up and sign-in, a chat page that sends each question to the Space, and per-user history with search.

The Model Side

  • Hosted separately: The question-answering model was a Gradio app on Hugging Face Spaces, called by name from Django
  • Interface: One input (question) and one text output from the /predict endpoint
  • Not in this repo: The corpus, embedding model, vector store and LLM used by the Space are not part of this codebase, so they are not described here
  • Stated scope: The site copy describes the intended scope as the Quran and hadith from the six major collections

Answers and Sources

  • Single string: The Space returns the answer as text; the app stores and renders it under the question as-is
  • No separate references: The call returns no retrieved passages, source list or score, so the app cannot show collection, hadith number or grading separately from the answer text
  • Random hadith widget: A landing-page button shows the Arabic text of a random Sahih al-Bukhari entry from a public API, without the collection name or number on screen

Django Backend

  • Server-rendered pages: Five routes (home, login, answer, logout, search); the chat is an HTML form POST with CSRF protection, not a JSON API
  • Synchronous model call: Each question creates a gradio_client client and waits for the answer; no streaming and no timeout
  • Accounts: Custom Login model with passwords hashed by Django's make_password; the signed-in email is kept in the Django session
  • History and search: Every question and answer saved per user, newest first, searchable with icontains on either field
  • No conversation context: Each question is sent to the model on its own

Challenges & Solutions

Challenge: Splitting the Work

Six people had to build a model and a website in parallel without blocking each other.

Solution: A Hosted Model Behind One Call

The model side published a Hugging Face Space and the web side called it through gradio_client. The trade-off: the web app can't see what was retrieved, so it can't tell retrieval errors from generation errors.

Challenge: Model Outages

The Space could be slow or unavailable during use.

Solution: Keep the Question

On any error the user sees the error message and the question is still saved, with a placeholder apology as the answer. That keeps history complete, but stores placeholders as if they were answers.

The app delivered the full user flow: sign up, ask a question, read the model's answer, and search past answers. The repository has no tests and no evaluation set, so there is no recorded accuracy or latency figure for the answers.

The gaps it left (no visibility into retrieval, no evaluation, no separate source references) are the ones I closed later in production RAG at Waffarha, with retrieval and end-to-end scored separately on a 225-case suite and deterministic gates in front of the model.
