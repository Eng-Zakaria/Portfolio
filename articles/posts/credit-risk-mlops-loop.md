**Evidence: Portfolio, synthetic data.** This is a personal project. Every applicant in it is generated by a script, and the repository holds no saved training run, so this write-up describes the design and the code, not measured model performance.

## The problem

A credit model is only useful if it sits inside a process: data comes in, features are built the same way every time, a model is trained and checked against minimum standards, the winner is deployed, applications are scored and turned into a decision, and someone watches for drift so the model gets retrained before it goes stale. Most portfolio credit projects stop at a notebook with an AUC. I wanted the surrounding machinery: a training pipeline with a validation gate, a scoring API that returns a decision rather than a raw probability, and scheduled jobs for retraining and monitoring.

Because there is no real bureau data to use, the project starts with its own generator.

## Architecture

```text
 credit_data_generator.py         100,000 synthetic applications, target default rate 15%
            |
            v
 FeaturePipeline                   stratified 70/10/20 split, then fit on train only:
 (winsorize + scale + target enc)  median fill, 1-99% clipping, StandardScaler, TargetEncoder
            |
            v
 TrainingPipeline / training DAG   XGBoost, LightGBM, CatBoost (early stopping on val)
            |                      metrics + params logged to MLflow (local ./mlruns)
            v
 ModelValidator                    fail if test AUC < 0.70, Gini < 0.40, KS < 0.30
            |                      warn on train/test AUC gap > 0.05, PSI > 0.20
            v
 deploy_model                      copy best model dir -> models/production
            .
            .  (not connected: API loads models/ensemble)
            .
 FastAPI /predict                  PD -> risk band -> APPROVE / REVIEW / DECLINE

 monitoring DAG (daily 06:00)      PSI + KS drift on 4 columns -> branch -> retrain stub
```

The code lives in one Python package (`src/`): a data generator, a feature pipeline, model wrappers, evaluation and validation, drift and performance monitors, a DuckDB data mart, and a FastAPI app. Two Airflow DAGs in `pipelines/` wire the training and monitoring steps, and `docker-compose.yml` defines containers for the API, a training job, an MLflow server, a Streamlit dashboard, and an optional Airflow profile.

## Decision 1: generate the data, and know exactly what the label depends on

The generator builds demographics, credit history, loan terms and utilization with correlated draws (credit score rises with age and income, interest rate falls with credit score, and so on). The default flag then comes from a hand-written logistic formula:

```python
log_odds = (
    -3.0
    - 0.02 * (df['credit_score'] - 650)
    + 0.05 * df['dti_ratio']
    + 0.3 * df['delinquency_2years']
    + 2.0 * df['bankruptcies']
    + 0.15 * df['num_credit_inquiries_6m']
    + 0.02 * df['credit_utilization_ratio']
    - 0.00002 * df['annual_income']
    + 0.00002 * df['loan_amount']
    - 0.02 * df['employment_length']
    + np.random.normal(0, 0.5, n)
)
```

After sampling, labels are flipped at random to hit the configured 15% default rate.

The upside is control. I know the true signal, so I can check whether the model recovers it, and I can rerun everything from a seed. The downside is that any score on this data measures how well a tree ensemble fits a logistic formula with noise. It says nothing about real borrowers, and a high AUC here would be expected rather than impressive.

I also checked for label leakage. No feature is computed from `default`, and the target encoder is fitted on the training split only, so the test set does not leak into the encodings. Two details are worth knowing. `bankruptcies` carries the largest coefficient in the formula, but it is not in the configured feature list, so the model never sees it. And `risk_score_bucket` and `interest_rate` are both derived from `credit_score`, which adds redundancy but not leakage.

## Decision 2: a hard validation gate before anything ships

Training and deployment are separated by `ModelValidator`. The training DAG trains the three boosters in parallel, picks the best one by test AUC, and then runs the validator. If the model misses any minimum, the task raises and the deploy step never runs:

| Check | Threshold | Effect |
|---|---|---|
| Test AUC-ROC | ≥ 0.70 | failure blocks deploy |
| Gini (2·AUC − 1) | ≥ 0.40 | failure blocks deploy |
| KS statistic | ≥ 0.30 | failure blocks deploy |
| Train − test AUC gap | ≤ 0.05 | warning |
| PSI, train vs test scores | ≤ 0.20 | warning |
| Default rate by score decile | non-decreasing (0.01 tolerance) | warning |

The trade-off is that only the three discrimination metrics can block a deploy, while overfitting, score shift and decile ordering just log warnings. I chose that because a fixed tolerance on a synthetic dataset is easy to trip by chance, and a pipeline that stops for every warning tends to get its checks switched off. The cost is that a model with a 0.08 overfit gap would still ship. In a real lender I would make the gap and decile ordering blocking and send warnings somewhere a person reads them.

The gate also checks discrimination but not calibration. `metrics.py` can compute a Brier score and expected loss (`PD × LGD × EAD` with LGD defaulting to 0.6), but the validator does not test them, even though the decision bands below depend on the probabilities being well calibrated.

## Decision 3: return a decision, not just a probability

The API converts the PD into a band and an action:

| PD | Risk category | Decision |
|---|---|---|
| < 0.10 | Very Low Risk | APPROVE |
| 0.10 – 0.20 | Low Risk | APPROVE |
| 0.20 – 0.30 | Moderate Risk | REVIEW |
| 0.30 – 0.50 | High Risk | REVIEW |
| ≥ 0.50 | Very High Risk | DECLINE |

A wide REVIEW band is a deliberate choice. Scores between 0.2 and 0.5 go to a person instead of being auto-declined, which costs analyst time but keeps borderline applicants out of an automatic rejection. The cut-offs are hard-coded constants, not tuned to a cost matrix or an approval-rate target, and the `confidence_score` field (`|0.5 − PD| × 2`) is a distance from 0.5, not a statistical confidence.

The API also fills in features the request does not include: `interest_rate` is fixed at 15.0, `credit_history_length` is estimated from employment length, and `total_credit_utilized` from income. That keeps the request small, but it means the API scores a different feature distribution from the one the model was trained on.

## Where the loop is still open

The repository has every component of a score-and-decide loop. The connections between them are what is missing.

!!! note "Gaps in the current code"
    - **Deploy and serve point at different places.** `deploy_model` copies the winner to `models/production/`, but the API loads `models/ensemble/` through `GradientBoostingEnsemble.load`. The default training run (`xgboost lightgbm catboost`) never writes `models/ensemble/`, so the API starts with no model and `/predict` returns 503.
    - **The request schema doesn't match the fitted pipeline.** The feature pipeline selects `income_category` and `risk_score_bucket` by name, and `/predict` doesn't build either column.
    - **Drift is simulated, and retraining is a stub.** The monitoring DAG samples 1,000 rows from the training file, subtracts 10 from `credit_score`, and runs PSI and KS on four columns. When drift is found, it calls a function whose `TriggerDagRunOperator` is commented out.
    - **`/metrics/{model}` returns constants** (0.85 / 0.70 / 0.55), not stored results.
    - **MLflow is used for tracking only.** Runs log parameters and metrics; models are saved with joblib, not registered.
    - **Built but not wired in.** The TabTransformer class and the stacking ensemble exist, but the CLI defaults train only the three boosters, the stacking ensemble is built with `use_tab_transformer=False`, and passing `tab_transformer` to the training pipeline raises "Unknown model type".
    - **No recorded results.** There is no `mlruns/`, no saved model, and no log in the repo, and the environment I checked lacks xgboost, lightgbm, catboost, mlflow and category_encoders, so I did not rerun it. The model table in the README has no run behind it.

## Results

There are no recorded model scores to report. What I can state from the code:

- The generator produces 100,000 rows at a 15% target default rate, with a 70/10/20 stratified split (`random_state=42`).
- Each model is evaluated on the held-out 20% using AUC, Gini, KS, log loss, Brier score and lift at 10% and 20%, and the deploy gate requires AUC ≥ 0.70, Gini ≥ 0.40 and KS ≥ 0.30.
- The test suite covers model fit/predict, metric calculations, PSI and data generation. The API test accepts either 200 or 503 from `/predict`, so it passes without a loaded model.

## What I'd do next

1. **Close the deploy-to-serve path.** Have the API load `models/production/` and its `metadata.json`, and add a test that trains a small model and gets a 200 from `/predict`.
2. **Use one feature builder for training and serving.** Move the derived-column logic out of the API into the feature pipeline, so a request goes through exactly the code the model was trained on.
3. **Record a real run.** Pin dependency versions, run the training once, and commit the metrics JSON next to the README so every number has a source.
4. **Make retraining real.** Compare recent scored applications against the training reference instead of a shifted sample, and enable the `TriggerDagRunOperator`.
5. **Gate on calibration.** Add a Brier or calibration-slope check, and choose the APPROVE/REVIEW cut-offs from an explicit cost of a missed default versus a lost good customer.
6. **Register models.** Log each model with MLflow and promote through the registry instead of copying directories.
